# Changelog

All notable changes to DbClone will be documented in this file. Date format: YYYY-MM-DD

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Database engines are now loaded as plugins from a `plugins` folder next to the application and are no longer compiled into it; adding a new engine means dropping its adapter into that folder — no code change in the application or UI
- Store / Restore operation — writes a connected database into a `.rdbx` catalog and restores one into a connected database, built on the DatabaseInterchange product contract
  - Store button on the Source connection panel and Restore button on the Destination connection panel — always visible, clicking either button sets the direction and starts the operation; keyboard shortcuts Ctrl+Shift+S and Ctrl+Shift+R
  - Restore asks what to do when the selected database already contains user objects: update the selected database after explicit confirmation, or create a new uniquely named database and restore there; cancelling leaves the destination unchanged
  - Pause/Stop controls always visible in the toolbar, enabled when a Store/Restore operation is running
  - Source and Destination are drawn as equal columns, so the two panels are the same width and reserve the same height whatever each one's own rows hold
  - Progress, log, and notification banner automatically show Store/Restore state — the progress card moves on the operation's own stages and objects (*Verifying catalog*, *Writing tables*, *Importing data 3/66 public.orders*, *Complete*) with the elapsed time and a status line beneath the bar, and the log pane and status bar state the run's own lines and outcome — and they keep showing it when the run ends, so a finished, failed or refused store/restore states what happened until Copy or Compare starts or the connection changes, at which point the active mode (Copy / Compare) takes the display back. A run that ends states its reason, not a count: the card stops on *Complete*, *Failed* or *Cancelled* and carries the same sentence the status bar, banner and log state — the product's own reason, or the first of several with how many followed it — so a restore that stops before its first stage no longer stands at *Starting / 0%* while a dismissible banner is the only place its cause was ever written. A run that failed reads as one: the ending and its reason are drawn on the card in the error colour the log already uses for its error lines, and a long reason wraps instead of being cut off at the card's edge
  - Store Options panel with catalog location, subfolder naming pattern, data inclusion and the catalog summary file; the naming pattern builds the catalog folder from `{Connection}` (the selected saved connection's name, so a connection called **Invoice matcher** stores as `Invoice_matcher_<timestamp>` instead of the `neondb` or `postgres` name a managed provider gives every project), `{Database}` and `{timestamp}`, and defaults to `{Connection}_{timestamp}` — `{Connection}` falls back to the source database name when no saved connection is selected, spaces and characters a folder name cannot hold become `_`, a name Windows reserves as a device is prefixed with `_`, and an over-long name is cut so the timestamp tail survives; chunk size, rows per chunk, snapshot consistency and unsupported-feature policy are read from `settings.json` and have no control in the panel yet
  - User manual section "Store & Restore" (F1) documenting both operations, what the catalog folder holds, and what a restore does and does not apply today
  - Catalog folder is picked in a folder browser when Store or Restore starts, the default folder can be changed in settings with a Browse button, and it is created automatically when it does not exist
  - Store captures the connected database into the catalog: schemas, tables with their columns, primary keys, indexes each stored with the key columns it covers as data beside the statement the server reported, check constraints and triggers, views and materialized views, functions and procedures, sequences, extensions, the dependency order between objects, row-level security policies, and the table rows — streamed with a server-side cursor so large tables do not have to fit in memory. Binary values (`bytea` columns) are always stored in individual files under the table's `blobs/` directory, never inline as hex; the row file keeps a reference (`@blob:<path>:0:<length>`) to the exact value file. The detected format (JPEG, PNG, PDF, etc.) is derived from the bytes themselves and recorded in the file name, never from a `content_type` column. Each file is directly usable and restore reads the referenced bytes without rebuilding hex text. Objects that only PostgreSQL understands (enums, domains, composite types, publications, subscriptions) are preserved as their original SQL and are re-applied only to a PostgreSQL catalog; tables without a usable key are stored in source order and say so. A partitioned table is stored with its parent, its strategy and its partition bound, and a sequence that belongs to a column records whether an identity column created it and says that the link a serial column draws from cannot be carried yet. Restore into a connected database binds the bytes of a container value straight to the target as a `bytea` parameter read from a stream over the referenced range — they are never converted back to hex and never held as one text value on the way in — while a binary value small enough to have stayed inline keeps its existing inline token. Restore is still being implemented, and it stops rather than pretending: it checks that the target is empty and reports what is already in it — naming the extensions, tables or other objects the database holds, rather than only saying it is not empty — then creates the catalog's schemas, installs the extensions the catalog records — each in the schema the source held it in, before anything that may name an object one of them provides, so an index over an extension's operator class is created instead of failing — and then creates the custom types, sequences and tables — a sequence an identity column created is left to that column, so the identity owns exactly one sequence instead of leaving an unused copy beside it — each table with its columns, defaults, generated and identity clauses, primary key, unique and check constraints, and each partition attached to the table it partitions — followed by functions and procedures, views (a materialized view comes back as its definition only, without its data), the foreign keys between tables, the indexes the source created by hand — an index that a primary key or unique constraint already made is left alone — and the triggers, each restored from the statement the server reported for it so its condition, its column list and the arguments it passes to its function come back intact; a trigger the source had switched off is switched off again. All of it happens in dependency order. The PostgreSQL-only objects are restored as well: the enums, composite types and domains the source declared are created before the tables that name them, from the captured statement, in the order one kind of type can depend on another — so a table with a column of a custom type now builds instead of failing with "type does not exist", a type name the source kept in mixed case comes back as the same name instead of a lower-cased one, and a domain keeps the check the server reported for it. A catalog that holds a publication or a subscription is not restored at all: the operation stops before it writes anything and names every object that nothing on the target can create, rather than filling the target first and then reporting the one object it left out. A catalog that holds any table also writes its rows back: the data files are read in batches and every stored value is handed to the server in the type the source column had, so a table whose column is a custom enum, domain or composite type comes back with its rows instead of failing on the way in, a column the server computes for itself is left to compute, and a timestamp keeps the instant it held even when the target server runs in another time zone. The rows are written in dependency order rather than in the order the catalog lists the tables, so a table whose name sorts before the table its foreign key points at comes back with its rows instead of being refused and left empty — and every table naming that one along with it. The restore then checks its own work: it counts what the target now holds — schemas, tables, views, materialized views, sequences, functions, procedures, enums, domains and composite types — and reads the row count of every table whose data the catalog recorded, reporting a difference as an error that names both numbers and a kind it cannot count as unchecked rather than passed, so a clean summary always stands for a check that actually ran. A restore that loses rows says so: the outcome states how many tables hold a different row count than the catalog recorded, out of how many the check compared, and the banner that reports it is styled by the error it found rather than by the fact that every object was created — a table whose rows the target refused is still an object the run created, so it stays in what the check answers, and the count no longer depends on the write having succeeded. A step that fails no longer ends the run at that step: the failure is one issue naming the step and the objects it cost, and every step after it still runs, so an index the server refuses costs the index instead of the tables, functions, views and rows that follow it. The two steps nothing else can be built on are the exception — a failed schema or table step is reported as a failed restore, and the rows are left unwritten rather than attempted against tables that are not there — and a check that cannot read the target is a warning saying the check did not run, never a failure of a restore that already landed. A store records only the schemas a restore can create: the engine's own system schemas are no longer carried as ordinary ones, because the server refuses their names in `CREATE SCHEMA` and every database it bootstrapped already holds them. A catalog captured before this rule still restores — the restore skips those names, and the count check answers each one from the target's own copy instead of reporting it missing — and the SQL script the store writes follows the same rule, so it no longer contains a statement the server rejects. Because a sequence's position is not in the catalog, restored rows keep the ids the source gave them while the sequence starts at its beginning, so the first row inserted after a restore can collide with a restored one until the sequence is moved forward. A subscription's statement is no longer written into the catalog at all, because `CREATE SUBSCRIPTION` embeds the publisher's connection string and a catalog is a file that gets copied; its name, the publication it reads and a note saying what was left out are recorded instead. Overwriting a populated database removes everything that check counts, including the extensions and publications that sit beside the schemas rather than in one, and drops each routine with the statement its kind needs — a procedure is no longer handed `DROP FUNCTION`, which the server rejects and which ended the pass, leaving every routine behind it: a database restored from the same catalog kept the extensions that restore installed, so choosing **Update selected database** cleaned the target and the restore that followed refused it as not empty. The question the UI asks before it overwrites a target is now the restore's own check, so the choice is offered for whatever a restore would refuse and the question names what the database holds; after the clean the same check is asked again, and a target that still holds something a restore refuses is not restored into — the run states what is left and starts nothing. A refused restore reports that sentence too, instead of a fixed "target database not empty". The report a restore ends with counts the target it actually produced rather than what the metadata reader's own filters kept: a schema the catalog records is put to the target by name before a difference is reported, so `public` — owned by the database's own role `pg_database_owner` from PostgreSQL 15 on and therefore left out of a read that leaves platform schemas out — is no longer reported as a schema the restore failed to create while its rows were written; extensions are counted among the objects checked, so a restore carrying one no longer ends saying it could not be checked for them; and `manifest.json` states how many schemas the catalog holds instead of reporting none beside a section that holds one. Database roles and permissions are still not read from the source at all
  - `summary.md` written into the catalog folder by Store and replaced on every store: statistics per table and per schema, a short list of what is unusual about the catalog (tables with no primary key, the tables the rest leans on, cyclic groups, foreign keys that leave the catalog, tables that take part in no relationship, pairs joined more than once), and every foreign key the catalog captured written out as a searchable register with a relation card for each table — nothing is dropped because the schema is large. Deliberately no diagram in this file: hundreds of lines crossing a page cannot be read, while the same facts in a list can be searched. The file names objects only — no host, user, password or connection string — so it is as safe to commit beside a catalog as the catalog's own text, and Restore never reads it: deleting, editing or replacing it cannot break a catalog. Switched off with the **Write summary.md** option in Store Options
  - The Store result now reports the rows, bytes and chunks the catalog really holds instead of zeros, and the log names the path of the summary file it wrote; stopping Store while the summary is being written stops only that file and still reports the finished catalog as complete
  - Store also writes the catalog's own SQL beside it — `sql/schema.sql` and `sql/data.sql`, or a numbered family under `sql/data/` when the rows do not fit one file — in the source database's own dialect, so a catalog can be run through `psql` or any SQL client on a machine that has no DbClone
    - Every statement may be run again: a second run creates no object and adds no row. A table with a primary key, or with a unique key every row must fill — all its columns declared `NOT NULL` and no `WHERE` narrowing it — inserts with `ON CONFLICT DO NOTHING`; a table without such a key inserts a row only when the target does not already hold it, so a nullable or partial unique key can never let a second run duplicate a row. Foreign keys are added unvalidated and validated at the end, and a trigger or a constraint that already exists is replaced instead of duplicated. An extension is installed from the name and the schema the catalog recorded, with the version the source carried deliberately not pinned, so a target that holds another version of it still loads and a second run installs nothing. A table that already exists is left as it is, and a sequence keeps the position its own declaration gives it, because a catalog records no current value. The table blocks are written in dependency order — a table the rows of a later block point at comes first, whatever the names sort like — and the rows are streamed into the file one batch at a time, so a table larger than memory still writes
    - The data script is sized rather than unbounded: 32 MB per file unless changed with the new **Largest data script file (MB), 0 = one file** option in Store Options. When the rows do not fit, they are written as a numbered family — `sql/data/0001.sql`, `0002.sql`, … in load order — where whole tables are packed into a file and a table too large for one file is continued in the next with `-- part N` in its banner, each part in its own transaction so a failure leaves every earlier part applied and re-runnable. The size bounds the file itself — the opening text of the first file and the key validation at the end of the last one count against it too — so the only way past it is a single `INSERT` larger than it. `0` keeps the single-file output byte for byte as it was, and a store whose rows fit one file keeps `data.sql` even when the finished file turns out larger than the size. A store that writes the family removes the `data.sql` an earlier store left, and a store that writes one file removes `data/` the same way, so the two shapes never appear together; a stale file the filesystem refuses to remove is named in a warning and never fails the store
    - A numbered family also gets `sql/load.psql`, which includes `schema.sql` and then every data file in the order they run, resolving each include against its own folder and deliberately not setting `ON_ERROR_STOP`; one file needs no driver, and a driver an earlier store left is removed when this store writes a single data file. The log names every file the store wrote and, for a family, the one command that loads it
    - `summary.md` gains an **SQL scripts** section naming every file — the schema, then each data file — with its size, statement and row counts, the layout the store chose and why, and the command that loads them, the guarantee and every limit, including the binary payloads that had to be inlined to fit into a file; the scripts are not part of the catalog's own bytes, and Restore never reads them
    - A pass that cannot write — a catalog recorded by another engine's adapter, a catalog in the direct format, an object the restore itself refuses, or a script role the adapter cannot even build — is one warning and no file rather than a failed store, and the same catalog always produces byte-identical files. Every file is built under a temporary name and all of them are moved into place only once the whole pass is complete, so a cancelled or failed pass leaves the scripts an earlier store wrote exactly as it found them. Switched off with the **Write SQL scripts (schema and data)** option in Store Options, on by default
- Database relationship explorer — read a database's relationships as one picture, either **live** from a connection or from a stored catalog without connecting to it: pan and zoom the table graph, filter by schema, search a table, column, constraint or comment, and follow references in either direction
  - The picture is arranged to be read top-down: a table stands under the tables it names, the table many tables name stands over the whole span of them, and every relation is one straight arrow between the two borders it joins, drawn behind the tables — a table standing between two others costs their relation nothing and never bends it round itself, and a relation a table draws to itself is the one curve, a loop out of its own top border and the only stroke that has to clear a card. A rank of tables too wide for the page is dealt in rows beneath the table it serves, so a wide catalog reads on one screen instead of stretching over a line several screens long. A catalog too large or too tangled for any arrangement to be proven still opens as a picture: the tables are drawn in the arrangement that came nearest to complete, so a table many tables name stays in the middle of the ring drawn around it instead of being flattened into the first arrangement tried, and the note beside the picture says its arrows are shown rather than proven
  - **View relationships** now sits under **both** connection panels: the source panel's button reads the source database and the destination panel's reads the target, so a database that was never stored can be looked at and nothing has to be remembered between sessions. The read touches no row — it reads the database's metadata (schemas, tables, columns, keys, constraints, indexes) and writes nothing back to it, asking the adapter for only that structure so a large database no longer waits for its routines, views, triggers, policies, publications, subscriptions, sequences, enums, domains and composite types before the picture appears. The folder button beside **Store** opens any stored catalog already on disk, and that route needs no connection at all, so a catalog can be explored on a machine that cannot reach the database it came from
  - The picture opens in DbClone's own window, which serves the document from memory and offers **Refresh** (reads the origin again — a table created after the window opened appears), **Open in browser** and **Save as HTML…**, which keeps the page exactly as it stands — a table carried by hand is saved where the reader put it, with its arrows drawn to it, instead of the arrangement the document was generated with. One window is reused instead of one per view. A machine that cannot host it falls back to the system browser and the log says why, and that fallback uses one fixed file, `%LOCALAPPDATA%\DbClone\view\relationship.html`, overwritten by every view — ten views, or a hundred, leave one file rather than one per view, per origin or per role. While the request runs the window states each phase in turn — *Reading the database model…* while the origin is read, then *Arranging the picture…* while the layout is worked out, each with a running elapsed timer — instead of claiming the read for the whole wait
  - The document fills the window instead of overflowing it: the stage takes the height the header, the chips and the toolbar leave over, the register under it gives its height back when the window is short, and the surface behind the page is the page's own colour, so no dark band shows before the first paint or beside it while the window is resized — and the picture fills that stage rather than only the canvas it was laid out on, so no table card is cut off at the canvas edge and the whole surface takes the drag, the wheel and **Fit** instead of only the part the canvas happened to cover
  - The picture opens on its own tables rather than on an empty corner of the canvas: a picture that fits the stage is centred in it, one larger than the stage starts at its own top-left corner, and **100%** and **Fit** both follow that rule — so 100% returns the reader to the tables and Fit fits the tables that are on screen, not the blank canvas they were laid out on. The picture keeps that place while the window is resized instead of being left against a band of empty stage, and a window that has not been laid out yet cannot pin it to the corner: a placement taken against a stage that measures nothing is refused and taken again once there is one. The box a placement is worked out against is measured before the new zoom is set, because that measure reads the page the window is leaving: taken afterwards it answers with the picture's size at the old zoom, and the tables are fitted against a blank stage instead of against themselves
  - The picture opens on the whole catalog: every table and every relation it holds is drawn when the view opens, whatever its size or how densely its tables reference one another — no count, no density rule and no legibility rule holds a table back from the first picture, and **Fit** brings all of it onto the screen
  - No view writes anything: the document is held in memory, so opening the view of a catalog leaves its files and their timestamps exactly as they were. A finished store still writes the picture **into** the catalog folder, named after it, so a catalog and the picture of it travel as one folder; like `summary.md` that picture is not part of the catalog's content — not listed in `manifest.json`, not hashed, never restored — so deleting or editing it cannot break a catalog, and a picture that could not be written is a warning naming the reason and never a failed store. A store that wrote its picture is not turned into a failed store by the line that reported it: the picture step reports on the thread the log belongs to, so a finished catalog ends as complete instead of ending on a threading error raised by its own progress line
  - A card per table, with the table's name and, on its second line, what the origin states about rows — the count the store captured, or the fact that a live read did not count them, because counting every table is a scan nobody asked for — and its width taken from its own text: `ai_chat_provider_configuration` gets a wider card instead of a name left outside a box, and no size or colour stands for a figure
  - Every foreign key drawn as its own arrow, from the table that stores the value to the table the value comes from; a dashed arrow and a dashed card mean the referenced table is not in the catalog, an arrow that curves is a relation a table draws to itself — every other relation is one straight line, and a table standing across it is drawn over the line rather than bending it — so a relation is drawn or the picture says why, never ruled out — a cycle is named in words in the panel of every table inside it, and a large group is drawn as one box you expand in place — with the pointer or from the keyboard, since the box takes the focus and Enter or Space opens it — and an arrow is selected by pointing anywhere in a wide invisible band beside its line instead of exactly on the stroke. The arrow now also states how many child rows may name a parent row: a bar at the child end means at most one, and nothing there means many rows or a pair the catalog cannot prove — the crow's-foot fork is gone, because many-to-one is the shape of nearly every key and a mark every line carries states the definition of a foreign key instead of a fact about the pair. Both marks are drawn on the line itself so they disappear with an arrow that a chip, the opening view or a collapsed group hides, and the key under the header now samples each shape and names the relationship the way ER editors do — `many-to-one (N:1)` for the plain arrow, `one-to-one (1:1)` for the bar — with one plain sentence beside the sample and no claim beyond a maximum — and it folds to a single line until it is opened, so the legend never costs the picture the screen it needs. The bar is derived, never guessed — the child's primary key or a unique constraint must cover exactly the referencing columns, so a relation whose uniqueness rests only on a unique index carries no bar rather than claim a proof the catalog cannot show — and a table that is only a link between two others is named where a sentence fits (`issue_labels · join table of issues and labels — inferred`) when its key is exactly the columns it points through, while a link table carrying a surrogate key is left unnamed instead of guessed at
  - Tables are arranged the one way. A table is placed under the tables it points at wherever the arrows allow it, so the picture reads top-down — but that is the order the arrangement is chosen by rather than a rule it is forced into: a group of tables that point at one another in a circle has no top, a family that surrounds its parent is drawn round it, and a table nothing joins stands clear of the rest instead of being squeezed in among the tables that are joined. The cards are spread far enough apart that an arrow between two of them has room to be drawn. Every relation is drawn as one straight line between the two borders it joins — never a set of right-angle turns and never a bow round anything — and the cards are painted over the lines, so a table standing between two others costs their relation nothing and no line is kept out of a card it does not join. Two straight lines may cross, and a crossing is read for what it is — two relations passing rather than a fault in either — so no arrow is bent round another to avoid one, no two arrows are ever drawn on one stroke, and the loop a table draws to itself is the one stroke held clear of every card. Every arrow is given its own point on the border of the card it joins, a mark's width and a clear gap apart, so two arrows that point at the same face land beside one another instead of fusing into one thick arrow belonging to no constraint in particular, and a table that more constraints reach than its border can hold is drawn wide enough to carry them all — widened across the tables that name it, so each arrow leaves the border where its own table stands. Reading a database and arranging its picture takes seconds, so the window opens before the work does: **View relationships** opens the viewer on the spot, naming the origin it is about to read and the panel the request came from, with a progress bar that stays until the picture replaces it — the pointer takes the waiting shape only where there is no window to say anything (the system-browser fallback), from the moment the request is made until that page exists, and puts that shape back whether the run finished, failed or was cancelled — while the arrangement is worked out beside the window's own thread instead of on it, so the application still answers while the picture is being made. A read that fails, or an arrangement that stops, is stated in that same window with the reason instead of leaving a progress bar that never turns into a picture. A chip that draws the same catalog again, which is the other arrangement a reader waits for, wears the waiting pointer on the view window itself while the new arrangement is computed. Where a card stands is the reader's judgement before it is the layout's, so a table can be taken hold of with the pointer and carried to another place — its own arrows are drawn again from card to card as it goes, the ring a table draws to itself travels with it, and pointing at the card twice puts it back where the layout drew it — while a chip that draws the picture again starts from the layout's own places, because a hand-moved card is a reading of this picture and not a new arrangement of the catalog. Nothing about the arrangement is switched by the reader: several starting points are tried — a top-down one, a radial one and a force-directed one — each is repaired until every relation is routed, and only the complete ones compete, the radial one walking each ring's own relations so that tables naming one another stand beside one another and then turning its tables along their rings, and widening a ring, wherever that clears a relation from a table standing over it, so the arrows of the table most others name run through open ground instead of behind other cards; they are compared first on how many arrows are drawn across one another, then on how many relations climb up the page, then on how long the total run of ink is. A crossing is never traded for a shorter arrow and no arrow is bent to avoid one, so a catalog whose arrows would have to climb across the page is drawn with the fewest of them climbing rather than turned inside out for the sake of it, and a chain or a tree read straight down keeps its top-down reading. A catalog whose tables fall into sets that reach nothing outside them is arranged as that many pictures, each from a starting point of its own, the pictures stood side by side at the line length that leaves the smallest page, so a family is never hung inside another family's picture. The search is bounded: twenty seconds is the ceiling, and reaching it is not the end of the picture — the arrangement keeps every table and every relation drawn by the same rules, with the crossings the starting points it tried happened to give, and the log says so beside the view — while the pass that lowers crossings is given a slice of what the picture left over, so a catalog the search has already answered is never made to wait for it; an arrangement the reader can look at is worth more than a statement that there is none, so the picture is drawn even when the search proves nothing — the plain arrangement, every table and every relation in one straight line each, is named beside the view with a warning that some relations may cross one another, so a large catalog is never answered with nothing at all — and the picture is handed over once, when it is the arrangement the search settled on, instead of a plain one that a refined page replaces a moment later, because a page that changes under the reader reads as two answers rather than one.
  - The columns a constraint joins are never written along its arrow: they sit beside it and appear when you point at an arrow or select it (`customer_id → id`), so a corridor carries its line and nothing else and two routes that converge never stack their text on each other; the panel and the register print every constraint's columns in full at any size, so no fact is behind the gesture alone
  - A bar of chips for the schema, the cyclic groups and the tables in no relationship — a click switches a cluster off, alt-click shows only it — where a single-schema catalog simply states its schema. Switching a cluster off draws the picture again without its tables, so the cards that remain close up the space those tables held instead of standing around an empty lattice, and every chip stays in the bar so the cluster comes back with one click; the count line keeps stating the catalog's own totals, and refreshing the view keeps the clusters that are on. The zoom is kept with them, so switching a cluster off or re-reading the origin changes what is drawn and never how closely you are reading it — and the place is kept too whenever the tables drawn again still stand where you were looking, while a place that the new arrangement leaves showing no table at all is put back on the picture instead of leaving you at blank canvas. Nothing places the picture behind your back: dragging, zooming, **Fit** and **100%** all hand the camera to you, so wheeling in on a table, panning to a corner and resizing the window leave the picture exactly where you put it
  - Each axis of the chip bar filters on its own, so switching a schema off hides every table of that schema even when a cyclic group also claims it, and a collapsed group's box leaves with the tables it stands over instead of naming tables that are no longer on screen
  - A panel that describes the selected table itself, without sending the reader to the catalog's JSON: its row count, its columns with type and key marks, its primary key, its unique constraints, its indexes — each named by the key columns the store captured, so a reader never has to read a SQL statement to find out what an index covers, with the statement the server reported printed only for an index whose columns the folder does not state — and its check constraints with their expressions. Below that, both lists of constraints, each row naming the constraint, the columns it joins, its `on delete`/`on update` action and how many child rows may name a parent (`exactly one`, `at most one`, or whether a child row may have no parent at all), so two constraints joining the same column pair are told apart by name and rule instead of reading as duplicate lines. Beside it, a register of every constraint in the catalog with its columns, its `on delete` and `on update` actions and its rule; two constraints between the same pair stay two arrows you can select one at a time
  - Searching reaches every table in the picture the reader is looking at: the result list names the field each row matched, and selecting a row shows that table — a table outside the neighbourhood the picture opened on or folded into a cyclic group is revealed and brought into view before it is selected, so a search never ends with a selection nobody can see. A cluster that is switched off is off the picture, and its chip in the bar is the one click that brings it back. An arrow is drawn only while both of the tables it joins are, so no line runs to a position where no card stands, and the count line under the header states what the picture is showing against the catalog's own totals (*Showing 7 of 66 tables · 6 of 10 relations — filtered*) whenever a chip narrows it
  - The picture states no figure its origin cannot supply: no per-table storage bytes and no time the catalog was stored, and a table comment is not shown at all because the catalog records none. Every sentence it speaks about its origin changes with the origin — the header (`catalog · folder · format version 4 · generated <t>` against `live database · host:port/database · read <t>`), a card's second line (`no data captured` against `rows are not counted here`), a table the picture does not hold (`not in this catalog` against `not in this view`), the register's rule column, the key under the header and the search field's label — so a live view reads as a live view and never as a catalog, and neither route prints a user name or a password
- Catalog verification now includes a tenth integrity check: every table declared in the catalog's tables section has a corresponding data folder, and every data folder is claimed by a table in the section — this catches the silent data loss that case-colliding table names could cause on case-insensitive filesystems
- Format version bumped to 4: row chunks are UTF-8 CSV files named `data.NNNNN.csv`, each with a BOM and complete column header; `manifest.json` records `data.encoding: "csv"` and requires a version 4 reader, while legacy NDJSON and catalogs written by an earlier version are refused with a request to store the database again. Every non-NULL binary value is stored in its own `blobs/<chunk>.<column>.<row>.<suffix>` file and the CSV carries only a reference. `table.json` contains bounded row and format counts, while `checksums.sha256` lists every row and blob file. A sequence now also records whether an identity column created it.

### Changed
- Internal architecture refactored onto a single-adapter boundary: the application now meets the database engine through one contract (`DbAdapter.Definitions`) with seven role interfaces (`IMetadataSource`, `IDatabaseAdmin`, `IDatabaseCleaner`, `ITableComparer`, `ICopySession`, `IConnectionStringSyntax`, `IPlatformResolver`), filled by `DbAdapter.PostgreSql`. Orchestration (connection verification, metadata reading, table filtering, permissions, backup, target cleaning, copy execution, result mapping) moved from the UI into `DbClone.Application` behind `ICopyWorkflow`, `ITableCatalogService`, and `IComparisonService`. The engine is reached only through an adapter catalog discovered from the `plugins` folder — no UI or Application file names an engine type, and `App.xaml.cs` registers the catalog rather than constructing an adapter. `CanonicalModel` holds the shared language (model records, copy options/results, platform data, enums); `DbAdapter.Definitions` holds the boundary DTOs (`DatabaseTarget`, `CopyRequest`, `AdapterInfo`) and the role interfaces. No user-visible behavior changes — Copy, Compare, and Backup work exactly as before
- Store/Restore streaming refactor: catalog writing and reading now stream rows one at a time instead of accumulating chunks in memory — a database of any size can be captured and restored inside a fixed memory budget. Chunk byte limit (`ChunkBytes`) and row limit (`MaxRowsPerChunk`) from settings are now honoured end-to-end; table selection filters which tables participate in Store; table folder names are resolved across case-colliding siblings before any folder is created, so `MixedCase` and `mixedcase` in the same schema produce two distinct folders instead of one overwriting the other; a collision is a fatal export error naming both tables, never a silent loss. Catalog inspection reads row counts from the manifest instead of re-parsing every row file
- Release builds run the Application, PostgreSQL, interchange, and UI test suites before the installer is built, and shipped logging defaults to Information with bounded file retention

### Fixed
- An unexpected error on the UI thread no longer closes DbClone without a word: it is written to the application log and to `%LOCALAPPDATA%\DbClone\crash.log`, and one window names the error before the application ends
- Store and Restore now preserve issue codes, affected object references, and details through the UI log, and a failed or refused restore reports its actual outcome instead of an unknown result
- Copy and Compare now resolve source and destination adapters independently, reject cross-engine operations before destructive work, and use adapter-owned copy connection handles for reopen and disposal
- Saved connections, groups, presets, and settings now replace JSON files atomically; corrupt persisted data is quarantined instead of silently becoming a file that a later save can overwrite
- Encrypted connection backups now use authenticated AES-GCM version 2 with atomic replacement while retaining compatibility with version 1 backups
- Explicit blob extraction now validates catalog folders and encoded output paths against their intended roots
- The About window's update check now reports that the check failed instead of claiming the app is up to date when the release feed could not be reached
- The table progress panel now moves while a table is being copied: row progress was reported only once per 5,000-row COPY batch, so every table smaller than that kept one figure for its whole copy and speed and ETA never left their first value — progress now follows the copy itself, at most ten times a second so the display is not flooded
- A copy that leaves platform schemas out no longer attempts the foreign keys that point into them: a constraint whose parent table is outside the copied scope is never sent to the server and is stated once per parent table (`SKIPPED: auth.users: 18 foreign key(s) not created — parent table is outside the copied scope`) instead of arriving as eighteen failed-constraint warnings in a run that still ended "Copy complete". The same constraint is no longer reported as a difference by Compare: when the parent is outside the compared scope the finding reads `FK not compared: <name> (parent <schema>.<table> is outside the compared scope)`, so a table whose only finding is such a constraint shows as a notice rather than a difference, while constraints whose parent is compared on both sides are compared exactly as before
- A copy no longer writes an ERROR line for a value it handles: reading a sequence's owned column from a destination that has no such sequence is an ordinary "no value" answer, so the false `Scalar query returned null` error is gone — and a statement that fails and is handled by its caller is no longer written to the log a second time as an `Error in ExecuteNonQueryAsync` line, because the caller states it once at the severity it belongs; the statement itself stays at Debug
- A copy that lost only a function, view, materialized view or trigger now ends **complete** with the count instead of claiming failure: each object the server refused is named once at warning severity (`FAIL: realtime.list_changes: permission denied for function list_changes`), the stage that tried to create it still reports `[OK]`, and the run ends `Copy complete in 241.1s — 1 object not created (see the log)`; a table that could not be created, rows that failed to copy or validate, and a refused index, sequence or composite type still end the run as failed
- A function whose definition sets a logging parameter is now created instead of being left out: before it creates functions, the copy asks for the settings privilege each function declares, so a destination role that may confer it no longer loses the function. The grant covers only the five logging parameters, is never revoked, needs PostgreSQL 15 or later on the destination, and a refusal is reported with the statement to run

### Security
- Auto-update verifies the downloaded installer against the SHA-256 the release publishes for it — the asset digest GitHub records, or a `.sha256` file beside the installer — and refuses to launch a download that does not match

- Table selection in Store/Restore is no longer decorative: the `Tables` and `ExcludedTables` filters from the UI reach the catalog writer through `ExportOptions`, so selecting specific tables now captures only those tables
- Case-colliding table names (e.g. `MixedCase` and `mixedcase` in the same schema) no longer silently overwrite each other on case-insensitive filesystems: the writer resolves collisions before creating folders and refuses to continue if a collision is detected, and the folder each table was written into is recorded in the catalog so a restore reads every one of those tables' own rows instead of guessing the name again — previously the second table's data was lost on export, and its rows were read back from its sibling on restore
- Application logs now live in `%LOCALAPPDATA%\DbClone\logs`, beside the app's other saved files and its `crash.log`, instead of the roaming profile — so a domain account no longer syncs them to the server — and the log folder is bounded: 10 MB per file with ten files kept (about 100 MB), oldest removed first, so a long copy can no longer grow it without limit. The application's own service logging reaches that file too (`ILogger` output now routes to the same Serilog file instead of stopping at the console and the Windows event log, whose write failure used to abort the operation that was logging)

## [1.1.0] - 2026-08-12

### Added
- Manual table selection: choose which tables Copy, Compare, and Backup process for a source database
  - Selection dialog with schema tree, search, sorting, table size column, and a foreign-key relationship explorer
  - Named presets stored per source connection + database with automatic restore of the last-used preset; unsaved (dirty) modifications survive application restart
  - Validation summary before applying a selection (dangling foreign keys, dependent views, orphaned partitions)
  - FK-aware behavior: unchecking a parent table automatically deselects its dependent child tables (recursively); re-selecting a child whose parent is excluded highlights the row with a warning
  - Compare ignores target tables outside the selection; views depending on excluded tables are reported as skipped
  - Copy and Backup clean only the selected tables on a populated destination, with an explicit choice: replace only the selected tables, or clear the entire destination
  - Resume/Update modes are blocked with an explanation while a non-default selection is active (they require "All Tables")
  - Destination table overview: read-only dialog listing all tables on the output database (schema tree, search, sorting, size column)
  - Destination database picker: when the destination has no database name, browse the server's databases and pick one directly from the main panel

### Fixed
- Sequence sync no longer fails for mixed-case names (e.g. serial sequences of `"MixedCase"` tables): sequence and owner-table identifiers are now quoted in `setval`/`pg_get_serial_sequence` calls, while the owner-column is passed unquoted so it matches the catalog literally
- Serial sequence sync no longer produces false "has no sequence on destination" warnings — the stage now resolves serial sequences by name and establishes the missing `OWNED BY` link on the destination
- Copy summary now lists each warning inline with its stage context (e.g. `SKIP [Extensions]: vector`) instead of "review warning entries above"
- Tables that fail to create (e.g. due to unsupported types or unavailable extensions) are now individually reported in the final warning summary with their specific error reason
- CopyData stage now explicitly logs which tables it skips because their creation failed earlier, instead of silently excluding them
- Copy summary "Tables:" count now includes all successfully processed tables (including empty ones), not just tables that had rows — previously "Tables: 3" when 16 tables were copied but only 3 had data
- Copy is now blocked with a clear error when a connection is missing a database name — Full/Resume/Update require a destination database (backup-only connections can only use Backup mode), and all modes require a source database; previously such copies reported success without copying anything
- Error banner and status display are now cleared when the connection or connection group is changed — previously an error from an earlier run remained visible after switching connections
- Connections, connection groups, table selection, and copy/compare options can no longer be changed while an operation is running — the controls are disabled until the operation finishes
- Connection failure error now shows which side (source/destination) failed and the configured host:port/database, instead of only the raw TCP error with a resolved IP
- Table selection now correctly excludes objects (sequences, triggers, policies, foreign keys) owned by partitions of excluded parent tables — previously only the explicitly excluded table's objects were filtered, leaving orphaned-partition dependents behind
- Table selection now skips materialized views that depend on an excluded table (same as ordinary views) — previously they were retained and could fail during creation
- Skipped-table tracking in the copy pipeline now uses the typed `TableId` key instead of fragile formatted strings — previously mixed-case table names could slip through and attempt data copy after their creation had already failed
